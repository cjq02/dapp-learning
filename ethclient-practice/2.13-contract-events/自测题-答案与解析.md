## Q1：为什么说「事件在以太坊中存储为日志」？事件和交易收据里的 Log 是什么关系？

**原题：**  
为什么说「事件在以太坊中存储为日志」？事件和交易收据里的 Log 是什么关系？

**你的解答：**  
因为事件在链上的存在形式是交易收据的日志，没有别的存储开工。发送的事件会记录为交易收据的一条日志。

**参考答案：**  
- **为什么这么说**：事件在链上**没有单独的存储形式**，其存在形式就是交易收据里的**日志**（Log）；合约执行时 `emit` 事件，等价于在收据中写入一条 Log。  
- **关系**：发出一个事件 → 在对应交易的收据里产生**一条** Log；Log 的 Address、Topics、Data 即该事件的链上表示。

**判定：** ✅ 正确（含义完整；「存储开工」应为笔误「存储形式」）

**得分：** 1.0 / 1

## Q2：topics[0] 一定是事件签名哈希吗？如果合约里同时有 Transfer(address,address,uint256) 和 Transfer(address,uint256)，如何区分不同事件的 topics[0]？

**原题：**  
topics[0] 一定是事件签名哈希吗？如果合约里同时有 Transfer(address,address,uint256) 和 Transfer(address,uint256)，如何区分不同事件的 topics[0]？

**你的解答：**  
topics[0]不一定是事件签名哈希，事件分为普通事件和匿名事件，普通事件topics[0]是事件签名，匿名事件topics[0]是第1个indexed参数。可以通过indexed参数区分。

**参考答案：**  
- **是否一定是事件签名**：**不一定**。普通事件的 `topics[0]` 是事件签名哈希；**匿名事件**（`anonymous`）不存事件签名，`topics[0]` 是第 1 个 indexed 参数。  
- **两个不同签名的 Transfer**：`Transfer(address,address,uint256)` 与 `Transfer(address,uint256)` 的**规范原型不同**，算出的 `keccak256(...)` 不同，因此 **topics[0] 本身就不同**，可直接用 topics[0] 区分；indexed 参数是次要的区分方式。

**判定：** ✅ 正确（匿名 vs 普通事件说对了；两个 Transfer 的区分主要靠不同的 topics[0]，你提到 indexed 也可辅助区分，不扣分）

**得分：** 0.9 / 1

## Q3：为什么被 indexed 修饰的字段不会出现在 Data 里？这样设计对查询和存储有什么影响？

**原题：**  
为什么被 indexed 修饰的字段不会出现在 Data 里？这样设计对查询和存储有什么影响？

**你的解答：**  
indexed修饰的字段是为了方便检索，Data里的数据通常是存储字符串、时间戳、金额这些。indexed参数可以方便筛选和过滤。

**参考答案：**  
- **为什么不在 Data 里**：设计上，indexed 参数被放入 **Topics**（每个 topic 一个 32 字节），便于节点建索引、RPC 按 topic 过滤；非 indexed 参数才按 ABI 编码放进 **Data**。所以 indexed 字段「不会出现在 Data 里」是因为它们被放在了 Topics 里。  
- **影响**：indexed 便于按条件筛选（如按 key、按地址查）；Data 存不需按条件过滤的值或变长类型；Topics 最多 4 个（普通事件 1 个给签名 + 3 个给 indexed），indexed 最多 3 个。

**判定：** ⚠️ 部分正确（说了 indexed 便于检索、Data 常存哪些内容，但未明确写出「因为进了 Topics 所以不在 Data」）

**得分：** 0.6 / 1

## Q4：如果只设置 FromBlock 不设置 ToBlock，FilterLogs 会查到哪个范围？想查「从某区块到最新」应该怎么设？

**原题：**  
如果只设置 FromBlock 不设置 ToBlock，FilterLogs 会查到哪个范围？想查「从某区块到最新」应该怎么设？

**你的解答：**  
如果不设置ToBlock，会查到最新的范围。想查「从某区块到最新」应该设置FromBlock，不设置ToBlock。

**参考答案：**  
- **不设 ToBlock 时**：查到**当前最新区块**（执行 FilterLogs 时节点认为的 latest），即 FromBlock～最新。  
- **「从某区块到最新」**：只设置 **FromBlock** 为起始区块，**不设置 ToBlock** 即可。

**判定：** ✅ 正确

**得分：** 1.0 / 1

## Q5：用 UnpackIntoInterface(&event, "ItemSet", vLog.Data) 时，为什么只传 vLog.Data 而不传 vLog.Topics？indexed 参数如何从日志里还原？

**原题：**  
用 UnpackIntoInterface(&event, "ItemSet", vLog.Data) 时，为什么只传 vLog.Data 而不传 vLog.Topics？indexed 参数如何从日志里还原？

**你的解答：**  
因为indexed参数在链上存在Topics。indexed参数可以从vLog通过topics获取。

**参考答案：**  
- **为什么只传 Data**：`UnpackIntoInterface` 的第三个参数是「待解码的字节」，事件里只有**非 indexed** 参数编码在 Data 中；indexed 参数在链上存在 **Topics** 里，不在 Data 里，所以只传 `vLog.Data` 就够解出非 indexed 字段。  
- **indexed 如何还原**：从 **vLog.Topics[1]、Topics[2]、Topics[3]** 按顺序取；需要时可用 ABI 的 `ParseTopics` 等按类型解析（如 32 字节 hash 或 padded 地址/数值）。

**判定：** ✅ 正确

**得分：** 1.0 / 1

## Q6：为什么订阅事件必须用 WebSocket 而不能用 HTTP RPC？从协议或模型上怎么理解？

**原题：**  
为什么订阅事件必须用 WebSocket 而不能用 HTTP RPC？从协议或模型上怎么理解？

**你的解答：**  
因为HTTP RPC只能请求和响应，而websocket可以保持长连接并推送。从协议或模型上，应该……

**参考答案：**  
- **为什么**：HTTP RPC 是**请求-响应**（一发一收），无法由服务端持续推送；订阅需要**服务端主动推送**新日志，必须用支持长连接与推送的通道。  
- **协议/模型**：HTTP 是「拉取」模型；WebSocket（或 IPC）是**长连接 + 服务端推送**，订阅属于「推送」模型，因此必须用 WebSocket（或 IPC）。

**判定：** ⚠️ 部分正确（前半句正确；「从协议或模型上，应该……」未写完整）

## Q7：query.Topics 是 [][]common.Hash，若 Topics[0] 放事件签名、Topics[1] 放某个 key 的 hash，这两个维度是「与」还是「或」的关系？

**原题：**  
query.Topics 是 [][]common.Hash，若 Topics[0] 放事件签名、Topics[1] 放某个 key 的 hash，这两个维度是「与」还是「或」的关系？

**你的解答：**  
这两个维度是与的关系。

**参考答案：**  
- **不同 topic 位置之间**：是 **与** 的关系。即日志必须同时满足 Topics[0] 匹配（事件签名）**且** Topics[1] 匹配（该 key 的 hash），才会被返回。  
- 同一位置 `Topics[i]` 里若有多个 hash，则是「或」（匹配其一即可）。

**判定：** ✅ 正确

**得分：** 1.0 / 1

## Q8：一笔交易可能触发多个合约的多个事件，receipt.Logs 里这些 log 的顺序由什么决定？如何判断某个 log 属于哪个合约、哪个 event？

**原题：**  
一笔交易可能触发多个合约的多个事件，receipt.Logs 里这些 log 的顺序由什么决定？如何判断某个 log 属于哪个合约、哪个 event？

**你的解答：**  
这此日志按合约代码执行顺序。log在链上记录了合约地址、普通事件的topics[0]记录了事件签名，通过这个可以定位合约和事件。

**参考答案：**  
- **顺序**：按**合约执行过程中 emit 的先后顺序**（即代码执行顺序）排列。  
- **判断合约**：看 **log.Address**（即 `vLog.Address`），每条 log 都带发出它的合约地址。  
- **判断事件（普通事件）**：看 **log.Topics[0]**，即事件签名的 keccak256 哈希；与预计算的 `keccak256("EventName(type1,type2,...)")` 比较即可识别是哪种事件。匿名事件无签名 topic，需结合合约地址和 ABI 推断。

**判定：** ✅ 正确（「这此」应为笔误「这些」）

**得分：** 1.0 / 1

## Q9：计算事件签名时为什么用 "ItemSet(bytes32,bytes32)" 这种字符串？参数名（例如改成 ItemSet(bytes32 indexed key, bytes32 value)）会不会影响签名？

**原题：**  
计算事件签名时为什么用 "ItemSet(bytes32,bytes32)" 这种字符串？参数名（例如改成 ItemSet(bytes32 indexed key, bytes32 value)）会不会影响签名？

**你的解答：**  
这是定义的规则。会影响。

**参考答案：**  
- **为什么用这种字符串**：以太坊 ABI 规定事件签名用**规范原型**：`EventName(type1,type2,...)`，只含**类型**，不含参数名、不含 `indexed`，类型用规范名（如 uint256）。这样与函数选择器规则一致，跨语言一致。  
- **参数名会不会影响**：**不会影响**。签名只认「事件名 + 参数类型列表」，所以 `ItemSet(bytes32 indexed key, bytes32 value)` 与 `ItemSet(bytes32,bytes32)` 的签名字符串相同，算出的 topics[0] 相同。

**判定：** ❌ 错误（「会影响」答反了；参数名**不会**影响事件签名）

**得分：** 0.2 / 1

## Q10：使用 SubscribeFilterLogs 时，若 sub.Err() 收到错误（如网络断开），只 log.Fatal(err) 退出是否合适？生产环境通常还要考虑什么（例如重连、背压）？

**原题：**  
使用 SubscribeFilterLogs 时，若 sub.Err() 收到错误（如网络断开），只 log.Fatal(err) 退出是否合适？生产环境通常还要考虑什么（例如重连、背压）？

**你的解答：**  
不合适。生产环境可以考虑重新连接，或者关闭连接。

**参考答案：**  
- **是否合适**：**不合适**。直接 `log.Fatal` 会立刻终止进程，无法做优雅恢复或告警。  
- **生产环境可考虑**：**重连**（带退避、上限）；**背压**（channel 消费不过来时不要阻塞发送端或丢日志）；**优雅退出**（context 取消、关闭 channel）；**告警/监控**（记录错误、上报）；必要时区分可恢复错误与不可恢复错误。

**判定：** ✅ 正确（判断对；重连、关闭连接都合理；若再写背压/告警更完整）

**得分：** 0.9 / 1
