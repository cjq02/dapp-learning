## 作业 1（01-query-events）

### Q1. 用 FilterLogs 查日志时，FilterQuery 里至少要填哪几个字段？不填 FromBlock 或 ToBlock 时，默认的区块范围分别是什么？

**你的解答：**  
至少要填2个字段，FromBlock和Addresses。如果FromBlock没填，范围会从最开始，如果ToBlock没填，范围会到最新区块。

**参考答案：**  
- **至少要填**：不填任何字段也可以查（全链、全区块），但通常用 **Addresses** 限定合约，用 **FromBlock/ToBlock** 限定区块范围；常见做法是填 Addresses，再视情况填 FromBlock、ToBlock。  
- **不填 FromBlock**：默认从**创世区块（0）**开始。  
- **不填 ToBlock**：默认查到**当前最新区块**（执行 FilterLogs 时节点认为的 latest）。

**判定：** ⚠️ 部分正确（不填 ToBlock 到最新、不填 FromBlock 从“最开始”说对了；但“至少要填 FromBlock 和 Addresses”不准确，FromBlock 可不填，默认从 0 开始）

**得分：** 0.7 / 1

### Q2. 为什么解码 ItemSet 时，UnpackIntoInterface(&event, "ItemSet", vLog.Data) 只传了 vLog.Data？event.Key 应该从哪里得到，为什么？

**你的解答：**  
因为UnpackIntoInterface解析的是事件的data。event.key要从topics得到。因为UnpackIntoInterface没解析topics

**参考答案：**  
- **只传 vLog.Data**：UnpackIntoInterface 的第三个参数是“待解码的字节”；链上只有**非 indexed** 参数在 Data 里，indexed 参数在 Topics 里，所以只传 Data 就只解出 value。  
- **event.Key 从哪得**：从 **vLog.Topics[1]** 得到（ItemSet 的 key 是第 1 个 indexed，占 topics[1]）；例如 `copy(event.Key[:], vLog.Topics[1].Bytes())`。  
- **原因**：UnpackIntoInterface 不会解析 Topics，只按 ABI 解 Data 段。

**判定：** ✅ 正确

**得分：** 1.0 / 1

### Q3. 若只想查某合约的 ItemSet 这一种事件，除了按合约地址过滤，还可以怎么设置 query.Topics？Topics[0] 应该填什么？

**你的解答：**  
设置ItemSet(bytes32,bytes32))，因为它是通过keccak256函数获取前4字节作为事件选择器。

**参考答案：**  
- **Topics[0]** 应填 **keccak256("ItemSet(bytes32,bytes32)")** 的**完整 32 字节哈希**（common.Hash），不是字符串本身。  
- 代码示例：`eventSig := crypto.Keccak256Hash([]byte("ItemSet(bytes32,bytes32)"))`，再 `query.Topics = [][]common.Hash{{eventSig}}`。  
- **区分**：函数选择器才是 keccak256 的**前 4 字节**；事件的 topics[0] 是**整 32 字节**的签名哈希。

**判定：** ❌ 错误（Topics[0] 填的是哈希值，不是字符串；且事件是 32 字节不是前 4 字节）

**得分：** 0.4 / 1

## 作业 2（02-subscribe-events）

### Q4. 订阅日志为什么必须用 WebSocket RPC（wss://）而不能用 HTTP（https://）？从“请求-响应”和“推送”的区别说明。

**你的解答：**  
因为Http是单向请求，而webSocket是长连接，可以收到服务端推送。

**参考答案：**  
- HTTP 是**请求-响应**：客户端发请求，服务端回一次就结束，无法持续推送。  
- WebSocket 是**长连接**，服务端可以**主动推送**新日志；订阅是“有新区块/新日志就推给你”的模型，必须用支持推送的通道（wss 或 IPC）。

**判定：** ✅ 正确

**得分：** 1.0 / 1

### Q5. defer sub.Unsubscribe() 的作用是什么？如果不调用 Unsubscribe 就退出程序，可能有什么问题？

**你的解答：**  
defer sub.Unsubscribe()的作用是关闭订阅。如果不调用，订阅程序会一直占用资源，无法释放

**参考答案：**  
- **作用**：在函数退出时（无论正常 return 还是 panic/Fatal）关闭订阅：向节点发送取消订阅、释放本地 channel 和连接资源。  
- **不调用的后果**：订阅和 WebSocket 连接可能不释放，占节点与本地资源；若节点对订阅数有限制，可能影响后续订阅。

**判定：** ✅ 正确

**得分：** 1.0 / 1

### Q6. 在 case vLog := <-logsCh: 里解码 ItemSet 时，除了用 UnpackIntoInterface 解 vLog.Data，为什么还要单独处理 event.Key？和作业 1 里的原因是否相同？

**你的解答：**  
因为UnpackIntoInterface传的参数vLog.Data，只有事件的data，不包含topics。原因相同。

**参考答案：**  
- 原因：UnpackIntoInterface 只解 Data，indexed 的 key 在 Topics[1]，不会通过 Data 填进 event.Key，所以需要单独从 vLog.Topics[1] 拷贝到 event.Key。  
- 与作业 1 相同：都是“Data 里只有非 indexed 参数，key 在 topics 里”。

**判定：** ✅ 正确

**得分：** 1.0 / 1

## 作业 3（03-events-from-receipt）

### Q7. 一笔交易可能产生多条 log（例如调用了多个合约或多次 emit）。要只处理其中的 ItemSet 事件，应该依据 log 的哪个字段判断？判断条件怎么写（用伪代码或一句话说明）？

**你的解答：**  
通过TxHash来判断。

**参考答案：**  
- **依据**：**log.Topics[0]**（事件签名哈希）。同一笔交易的多条 log 有相同 TxHash，无法用 TxHash 区分“哪条是 ItemSet”。  
- **判断**：若 `len(vLog.Topics) > 0` 且 `vLog.Topics[0] == keccak256("ItemSet(bytes32,bytes32)")`，则该条 log 是 ItemSet 事件。

**判定：** ❌ 错误（TxHash 只能区分交易，不能区分同笔交易内的不同事件类型）

**得分：** 0.2 / 1

### Q8. 事件签名哈希 eventSig 是用什么字符串做 keccak256 得到的？如果 Solidity 里写成 event ItemSet(bytes32 indexed key, bytes32 value)，计算签名时参数字段名（如 key、value）要不要写进这个字符串？为什么？

**你的解答：**  
eventSig是用事件名和参数类型。key和value不用写进字符串，因为keccak256解析的是函数名和参数类型，参数名称不需要。

**参考答案：**  
- **用的字符串**：规范原型 **"ItemSet(bytes32,bytes32)"**，只含事件名和参数**类型**，无空格、无参数名、无 indexed。  
- **参数名不写**：签名只认“事件名+类型列表”，参数名、indexed 不参与，所以 key/value 不写进字符串；这样不同命名下同一事件签名一致。

**判定：** ✅ 正确

**得分：** 1.0 / 1

### Q9. 从收据解析事件和用 FilterLogs 查历史事件，在“数据来源”上有什么不同？分别适合什么场景（一句话概括）？

**你的解答：**  
收据解析事件通过交易hash获取收据，从收据得到事件日志。FilterLogs是通过区块范围来查找事件。收据解析事件适合有明确的交易hash的情况，更快捷。FilterLogs需要查询指定范围的情况。

**参考答案：**  
- **数据来源**：收据解析 = 先有**交易哈希** → TransactionReceipt → 该笔交易的 receipt.Logs；FilterLogs = 指定**区块范围 + 地址等** → 节点返回该范围内匹配的日志。  
- **场景**：收据解析适合“已知某笔交易，要看这笔交易发了哪些事件”；FilterLogs 适合“按区块/时间范围扫某合约的历史事件”。

**判定：** ✅ 正确

**得分：** 1.0 / 1

## 综合

### Q10. 若 Store 合约改成 event ItemSet(bytes32 indexed key, bytes32 indexed value)（key 和 value 都 indexed），链上 log 的 Topics 和 Data 会怎样变化？解码时 Key 和 Value 应该分别从哪里取？

**你的解答：**  
如果这样改，Data会为空。topics[1]是key,topics[2]是value。解码时从topics获取。

**参考答案：**  
- **Topics**：topics[0] 仍是事件签名哈希；topics[1]=key，topics[2]=value（两个 indexed 各占一个）。  
- **Data**：无非 indexed 参数，**Data 为空**（0x）。  
- **解码**：Key 从 topics[1]、Value 从 topics[2] 取（各 32 字节）；不再用 UnpackIntoInterface 解 Data（因 Data 为空）。

**判定：** ✅ 正确

**得分：** 1.0 / 1

## 小结

- **Q1**：FilterQuery 不填 FromBlock 时默认从 0 开始，并非“必须填 FromBlock”；“至少要填”的说法改为“通常填 Addresses，再按需填区块范围”更准确。  
- **Q3**：Topics[0] 填的是 **keccak256("ItemSet(bytes32,bytes32)") 的 32 字节哈希**，不是字符串；事件用整 32 字节，不是“前 4 字节选择器”。  
- **Q7**：区分“哪条 log 是 ItemSet”要看 **Topics[0]**（事件签名），不是 TxHash（TxHash 只能区分不同交易）。
