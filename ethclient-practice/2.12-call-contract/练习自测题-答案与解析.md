## 练习 01（读取合约）

### Q1：用 abigen 生成的合约读数据时，为什么要传 nil 给 Version(nil) / GetItem(nil, key)？这个 nil 代表什么？

**你的解答：**  
因为 abigen 生成的 go 文件，version 方法定义了 *bind.CallOpts，是 eth_call 的参数的可选项，传 nil 表示不设置任何值。但是不能不传。

**参考答案：**  
- 第一个参数类型是 `*bind.CallOpts`，用来配置 eth_call 的选项（如查询哪个区块、是否用 pending 状态等）。  
- 传 `nil` 表示使用**默认选项**（当前最新区块、非 pending），等价于 `&bind.CallOpts{}`。  
- 方法签名要求必须传该参数，所以“不设置任何特殊选项”时就传 `nil`。

**判定：** ✅ 正确

**得分：** 1.0 / 1

### Q2：合约里 GetItem 返回的是 bytes32，在 Go 里拿到的是 [32]byte。若当初存的是短字符串（如 "hello"），为什么直接打印会看到后面一长串 0？要变成人类可读的字符串，思路是什么（用一句话说明）？

**你的解答：**  
因为返回的数据是 bytes32，表示占用了 32 位字节，短字符串占用的字节数如果不足 32 位，就会补零。思路是：先把 bytes32 的数据强转成 string，再通过 trim 方法把零去掉。

**参考答案：**  
- 原因：bytes32 固定 32 字节，存短字符串时只占前面若干字节，后面用 0 填充，所以直接打印会看到一长串 0。  
- 思路：将 `[32]byte` 转成 `string`，再用 `TrimRight(..., "\x00")` 去掉尾部零字节，得到实际字符串。

**判定：** ✅ 正确（“补零”“trim 掉零”都对）

**得分：** 1.0 / 1

### Q3：从控制台读入的 key 是字符串，而 GetItem(nil, key) 要的是 [32]byte。在 Go 里从 string 得到 [32]byte 的常见两步是什么？

**你的解答：**  
从控制台读到的字符串，要先去掉换行符。定义字节数组 key，将字符串强转成 []byte 切片，再 copy 到字节数组。

**参考答案：**  
- 先对读入的字符串做 TrimSpace（或 TrimRight 换行），去掉首尾空白/换行。  
- 定义 `var key [32]byte`，用 `copy(key[:], []byte(keyStr))` 把字符串的字节拷贝进数组，不足 32 字节的部分保持为 0。

**判定：** ✅ 正确

**得分：** 1.0 / 1

## 练习 02（写入合约）

### Q4：调用 SetItem 前为什么要先 bind.NewKeyedTransactorWithChainID(privateKey, chainID) 得到 auth？auth 里主要包含哪些对发交易有用的信息（说 1～2 点即可）？

**你的解答：**  
因为 SetItem 在合约方法属于交易，交易需要传入 privateKey，NewKeyedTransactorWithChainID 得到的 auth 返回的是 *bind.TransactOpts，通过 abigen 生成的 setItem 方法第一个参数就是 *bind.TransactOpts。auth 里包含发送方地址、GasPrice、GasLimit 等。

**参考答案：**  
- 写函数会发交易，需要签名；auth（*bind.TransactOpts）由私钥和 ChainID 生成，内部包含签名所需信息，abigen 生成的 SetItem 第一个参数就是它。  
- auth 里可包含：From 地址、GasLimit、GasPrice、Value（随交易发送的 ETH）等，用于构造并签名交易。

**判定：** ✅ 正确

**得分：** 1.0 / 1

### Q5：storeContract.SetItem(auth, key, value) 返回的 tx 能直接说明“链上已经执行成功”吗？要如何判断交易是否成功、以及实际消耗了多少 gas？

**你的解答：**  
tx 不能直接说明。可以调用 bind.WaitMined，等待交易结果。

**参考答案：**  
- 不能。tx 只表示交易已提交到节点，尚未打包进区块。  
- 应用 `bind.WaitMined(ctx, client, tx)`（或轮询 `client.TransactionReceipt`）拿到 receipt 后，用 **receipt.Status == 1** 判断是否成功，用 **receipt.GasUsed** 看实际消耗的 gas。你只写了“等待交易结果”，未明确写出“看 receipt.Status 和 receipt.GasUsed”。

**判定：** ⚠️ 部分正确（“不能”和“WaitMined”对；缺少“用 receipt.Status / receipt.GasUsed 判断成功与 gas”）

**得分：** 0.7 / 1

### Q8：parsedABI.Pack("setItem", key, value) 得到的 input 在交易里对应哪个字段？这串字节里前 4 个字节一般叫什么？是怎么来的？

**你的解答：**  
对应的是交易方法的 data 字段。这串字节的前 4 字节叫函数选择器。通过 keccak256 计算出来的。

**参考答案：**  
- 对应交易的 **Data** 字段（调用数据）。  
- 前 4 字节叫**函数选择器（selector）**。  
- 计算方式：对**函数签名**（如 `"setItem(bytes32,bytes32)"`）做 **Keccak256** 哈希，取**前 4 字节**。你写“keccak256 算出来的”方向对，但未写清是“函数签名的 Keccak256 的前 4 字节”。

**判定：** ⚠️ 基本正确（data、选择器、keccak256 都对；选择器来源可更精确）

**得分：** 0.9 / 1

### Q9：用 client.CallContract 做 eth_call 读 getItem 时，需要哪三样东西：构造什么消息、调哪个 API、以及如何从返回的字节里解析出 bytes32？

**你的解答：**  
构造什么消息：合约地址和参数。调哪个 API：不知道，难道是 GetItem?。如何从返回的字节里解析出 bytes32：调用 abi.ABI 的 UnpackIntoInterface 方法。

**参考答案：**  
- **构造消息**：`ethereum.CallMsg{ To: &contractAddress, Data: callInput }`，其中 callInput 由 `parsedABI.Pack("getItem", key)` 得到（即合约地址 + 打包后的调用数据）。  
- **调用的 API**：`client.CallContract(ctx, callMsg, nil)`（是 RPC 的 eth_call 封装）。  
- **解析**：用 `parsedABI.UnpackIntoInterface(&unpacked, "getItem", result)` 把返回的 result 解析进 `[32]byte`。  
你“构造消息”只说了合约地址和参数，未明确 CallMsg 和 Data；“调哪个 API”应为 **CallContract**，不是 GetItem；“UnpackIntoInterface”对。

**判定：** ⚠️ 部分正确（解析对；构造消息不完整；API 答错）

**得分：** 0.5 / 1

### Q10：types.SignTx(tx, types.NewEIP155Signer(chainID), privateKey) 里为什么要传 chainID？不传或传错会有什么问题（说一点即可）？

**你的解答：**  
传 chainID 是为防重放。不传的话，可能导致交易失败或者是安全问题。

**参考答案：**  
ChainID 用于 **EIP-155 签名**，防止同一条签名在不同链上重放。不传或传错可能导致：主网/测试网拒绝该交易（签名与当前链不匹配），或交易在错误链上被重放。

**判定：** ✅ 正确

**得分：** 1.0 / 1
